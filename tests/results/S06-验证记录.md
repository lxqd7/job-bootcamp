## S06-a 报价、订单快照与待支付锁（2026-11-20）

### 1. 需求与实现范围

- 需求：ORD-01/01A/01B/02/04、BUY-05、CRS-02。
- 新增服务：`bootcamp-trade`，端口 18084，独立库 `bc_trade`。
- V1 迁移：`price_quote`、`trade_order`、`order_course`、`order_lesson`、`pending_course`、`user_trade_guard`、`api_idempotency`。
- 接口：
  - `POST /api/v1/trade/quotes`
  - `GET /api/v1/trade/quotes/{id}`
  - `POST /api/v1/orders`（支持 `Idempotency-Key`，缺省用 quoteId）
  - `GET /api/v1/orders`
  - `GET /api/v1/orders/{id}`
- 课程内部接口：`POST /int/v1/products/snapshots`，返回课程版本、价格、状态、分类与活动小节/媒体时长；内部操作码 `products:snapshot`。
- 本小任务不接优惠券、支付、回调、发权与页面；券模式固定 `NONE`。

### 2. 关键实现

1. 报价只接受 `productType=COURSE`。课程必须 `ONLINE`、付费、价格不低于 990 分且至少有一节可播放视频；已拥有课程返回 `ALREADY_OWNED`，免费课提示直接领取。
2. 报价有效期 5 分钟，保存 `input_hash`、`result_hash`（quoteHash）、商品版本、金额和 JSON 快照。quoteHash 使用固定字段顺序的 canonical JSON + SHA-256，覆盖商品版本、标题/描述、价格、分类、小节 ID/媒体/时长和金额，不哈希查询时间。
3. 下单只接收 `quoteId`、`quoteHash`、`selectedCouponIds`，不接受客户端金额。事务内重新读取课程快照与学习权益，并重算 quoteHash；变化时把报价标记为 `STALE`，返回 `QUOTE_CHANGED`。
4. 同一用户同一课程用 `pending_course` 唯一键占用待付资格；已有待付时返回 `ORDER_CONFLICT`，`data.resourceId` 为已有订单 ID。`user_trade_guard` 行锁串行化同一用户的订单创建。
5. 订单先插入 `CREATING`，写 `order_course`、`order_lesson`、`pending_course` 后更新为 `WAIT_PAY`；订单有效期 30 分钟。`order_lesson` 保存本次新购付费课的完整活动小节及服务端时长快照。
6. 创建幂等分两层：`trade_order(user_id, request_key)` 唯一键保证只产生一单；`api_idempotency` 记录请求 hash、处理中/完成/失败状态，相同键的并发请求等待并返回同一订单，不同请求内容复用同一键返回 409。
7. 报价状态 `EXPIRED`/`STALE` 使用独立 `REQUIRES_NEW` 事务写入，避免下单事务回滚把失效证据一起抹掉。
8. 订单查询只允许本人；报价只允许本人；管理员与其他学生均不能通过交易接口读取或创建学生订单。

### 6. 理解问题与精简回答

1. **为什么下单不能直接接收客户端金额？** 客户端金额可被篡改；下单只信服务端报价与服务端商品/权益快照，金额从 quoteId 对应记录读取，并对快照重算哈希。
2. **quoteHash 和订单快照分别解决什么？** quoteHash 证明用户确认的是同一套商品版本、价格、权益和分摊结果；订单快照把成交时的商品与金额永久固化，后续改价不影响旧订单。
3. **100 个相同创建键为什么只产生一单？** `trade_order(user_id, request_key)` 唯一键是最终事实约束，`api_idempotency` 负责并发等待与结果复用，二者共同保证请求幂等而不是只靠前端防重复点击。
4. **pending_course 与订单状态为什么要分开？** 订单状态描述交易生命周期，pending_course 是“该用户该课程正在被占用”的技术锁，便于在创建、支付、关闭之间独立协调，避免同一课程被两个待付订单同时卖出。

## S06-b 模拟支付、回调、发权与退款通道（2026-11-20）

### 1. 需求与实现范围

- 需求：ORD-01/01A/01B/02/04、BUY-05、CRS-02。
- 支付渠道：`PaymentPort` 接口 + `MockPaymentAdapter`；仅 `PAYMENT_MODE=mock` 注册，真实渠道未接入。
- 新增表：`payment_request`、`payment`、`channel_receipt`、`refund`、`outbox_event`。
- 新增/扩展接口：
  - `POST /api/v1/orders/{id}/payment`：学生本人创建 MOCK 支付单。
  - `POST /api/v1/orders/{id}/cancel`：学生取消待付订单。
  - `POST /callbacks/payments/{channel}`：渠道回调，HMAC 验签，无登录。
  - `GET /api/v1/refunds/{id}`：学生查看本人 SYSTEM_RETURN。
  - `POST /api/v1/dev/payments/{id}/scenario`：ADMIN、开发场景；默认关闭。
- 网关增加支付回调、退款和开发场景路由；开发场景同时保留 `/dev/payments/**` 别名。

### 2. 关键实现

1. 学生支付请求只能支付 `WAIT_PAY` 且未过期的本人订单；同一订单/渠道复用 `payment_request`，不因 HTTP 重试新建。学生请求没有 `paidAt` 字段，`paidAt` 只来自渠道回调。
2. 回调先验 HMAC 签名，再校验商户请求、金额、CNY、回执编号和渠道时间；验签失败不落回执、不改订单。`channel_receipt` 以 `(channel,receipt_id)` 唯一，重复报文只处理一次。
3. 支付事实写入 `payment`，`channel_trade_no` 唯一；只有确认收款才写 payment。订单状态、支付流水、发权状态三者分离。
4. 有效支付严格使用渠道 `paidAt`：必须早于订单 `expires_at`，有取消意图时还必须早于 `cancel_requested_at`。到期前支付、通知晚到仍可转 `PAID`；到期后或额外收款不授予权益，创建 `SYSTEM_RETURN`。
5. 有效支付在本地事务内更新订单 `PAID`、`fulfillment_state=PENDING`、清 `pending_course`、写 `trade.payment-confirmed.v1` outbox。trade outbox relay 通过 Rabbit 投递；learning 建 `COURSE_ORDER` 来源和课程 grant，成功后回传 `learning.order-granted.v1`，trade 更新 `order_course.source_id/source_grant_id` 并置 fulfillment `DONE`。
6. 学习服务停机时 Rabbit 队列保留事件；恢复后 learning 幂等补发，trade 收到回执后完成 fulfillment。事件重复投递不会产生第二份来源或 grant。
7. 取消/到期先把订单置 `CLOSING` 并记录取消时间，再关闭渠道单；渠道返回 `CLOSED` 才释放 `pending_course` 并置 `CLOSED`，返回未知时保持 `CLOSING`，定时任务重试。
8. `SYSTEM_RETURN` 退款以 `system_return_payment_id` 唯一，金额为实际额外收款；MOCK 退款立即完成，S09 复用通道扩展用户退款。
9. MOCK 场景接口只在 `PAYMENT_MOCK_SCENARIO_ENABLED=true` 时注册，且控制器要求 ADMIN；学生不能调用。生产应设置 `PAYMENT_MODE=real` 并关闭场景。

### 6. 理解问题与精简回答

1. **为什么支付回调不能直接改订单为已支付？** 回调可能伪造、重复或金额/币种不一致；必须先验签、校验商户请求与金额，再以可信渠道 `paidAt` 判断是否在有效付款窗口内，最后才写支付事实和订单状态。
2. **为什么要区分订单 `PAID` 和 fulfillment？** 收款成功不等于学习服务已经授予；交易先记录已付，发权通过 outbox 异步完成，学习回执后才置 `DONE`，这样学习停机不会丢失权益，也不会把“已付款”误报成“已开通”。
3. **重复回调如何保证只发一份权益？** `channel_receipt` 以回执编号唯一，`payment` 以 `channel_trade_no` 唯一；learning 的来源以 `(user, COURSE_ORDER, orderId)` 唯一、grant 以 `(sourceId, courseId)` 唯一；每层都能独立幂等。
4. **到期前付款但通知晚到为什么仍有效？** 判断依据是渠道 `paidAt`，不是回调到达时间；只要 `paidAt < expires_at`（且没有更早的取消意图），即使订单已被本地关闭，也按真实早付恢复购买并授予权益。

### 5. 理解问题与精简回答

1. **为什么支付页不能根据按钮点击直接显示成功？** 按钮只发起模拟付款请求；订单是否已支付必须由服务端回调验签后写入，页面只能轮询服务端订单状态。
2. **为什么订单详情要区分“已支付”和“已开通”？** 支付事实与学习权益授予是两个状态；页面应显示 `PAID + PENDING` 的开通中状态，不能把已付款误显示成已可学习。
3. **管理员场景面板为什么不能改金额或直接标付款？** 它只触发统一 MOCK 回调处理器，让测试走验签、金额校验、幂等和发权链路；直接改数据库或前端伪标会绕过业务约束。
