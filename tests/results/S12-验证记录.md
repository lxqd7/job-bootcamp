## S12-a 教师双分配、单题版本与 epoch 绑定（2026-11-23）

### 1. 需求与实现范围

- 需求：BEN-01、BEN-01A、BEN-02、BEN-04（教师范围部分）、AUTH-02、AUTH-03。
- 教师福利题类型扩展为 BENEFIT_CHOICE（严格一道单选/多选）和 BENEFIT_CODE（一道代码补全题）。
- 创建/编辑/发布草稿要求教师同时负责课程和路线；路线必须 ONLINE 且当前包含该课程。
- 首次发布在同一作业库事务内绑定每条路线当前 epoch；之后内容更新生成新版本但不改绑定。
- 路线移除课程后重新加入会产生新 epoch；旧题保留旧 epoch，新范围必须另建福利题。
- 学生福利访问（双权益、历史 epoch、退款冻结）属 S12-b；教师页面/路线入口/福利作答属 S12-c。

### 2. 数据与接口

assignment V5：

- kind 扩展 BENEFIT_CHOICE/BENEFIT_CODE，scope 检查要求 chapter_id 为空。
- `assignment_route` 增加 `(route_id,epoch_id,assignment_id)` 索引。
- 福利题草稿 draft_json 带 routeIds；formal_scope_key 使用 `BENEFIT:courseId:uuid` 保持唯一。

教师 API：

- `GET /api/v1/teacher/benefit-assignments?courseId=&page=&pageSize=`
- `POST /api/v1/teacher/benefit-assignments`
- `GET/PATCH/DELETE /api/v1/teacher/benefit-assignments/{id}`
- `POST /api/v1/teacher/benefit-assignments/{id}/publish|offline`

课程内部：

- `POST /int/v1/teachers/benefit-scope`（HMAC `teachers:benefit-scope`）：返回课程/路线分配、路线 ONLINE、是否包含课程、当前 epochId。
- `CourseScopeClient` 新增 benefitScope；作业服务不再把教师分配缓存为长期授权。

### 3. 关键实现

1. 福利选择题严格 1 题；福利代码题复用代码 slot 校验；正式题仍按 1～50 题/课程代码题规则。
2. 创建和首次发布都调用课程内部双范围检查；教师未分配课程/路线返回 403，路线未发布或未包含课程返回 409。
3. 首次发布时在 assignment 行锁内读取 routeIds，逐条写入 `assignment_route(route_id, epoch_id)`；路线列表或 epoch 任一无效时整次发布失败。
4. 后续发布只生成新 assignment_version，不删除/重建 assignment_route；路线重新加课产生的新 epoch 不会自动重绑旧题。
5. 内容更新只允许作者本人且必须仍在课程/路线分配范围；首次发布前更换 routeIds 返回 409，要求另建新题。
6. 下架保留路线绑定和历史版本；已绑定/已发布福利题不能物理删除，未发布草稿可删除。
7. 管理员正式作业接口按 formal kind 过滤且拒绝福利题；学生正式作业列表同样只含 CHAPTER_CHOICE/COURSE_CODE，避免福利题绕过路线资格提前泄露。

### 6. 理解问题与精简回答

1. **为什么福利题要先有课程分配和路线分配？** 课程决定题目归属和学生学习权益，路线决定哪些学员能看到这道题。只校验一个都会让题目越权开放。
2. **为什么首次发布要绑定 epoch，而不是每次读当前路线？** epoch 是“这门课什么时候在路线里”的稳定区间。绑定后，路线以后移除/重加课程不会悄悄改变旧题可见人群。
3. **为什么路线重加课程后要新建福利题？** 新 epoch 代表新的开放范围；旧题仍服务历史学员。让旧题自动改绑会把旧答案/解析暴露给不该看到的新范围。
4. **为什么内容更新可以生成新版本但不改路线？** 题目内容修正和开放范围是两个维度；版本只改变题面/答案，不改“给谁看”，避免一次编辑意外扩大受众。## S12-b 学生双权益、历史 epoch 与冻结边界（2026-11-23）

### 1. 需求与实现范围

- 需求：BEN-03、BEN-04、BEN-05、BEN-06、AUTH-04。
- 学生访问福利题同时满足：课程有效学习权益 + 至少一条题目绑定路线在该绑定 epoch 上的有效路线福利资格。
- 历史 epoch：路线移除课程前购买且订单快照包含该课程的老学员保留已有福利题访问；移除后才购买路线的新学员不能访问旧 epoch 题目。
- 来源 FROZEN/REVOKED 后读取和提交立即拒绝；恢复 ACTIVE 后恢复访问。
- 题目下架拒绝新 attempt，已有提交仍可读；教师调离后福利题读取与下架均拒绝。
- S12-c 的教师页面、路线福利入口和作答页面未做。

### 2. 接口与实现

学习内部：

- `POST /int/v1/access/benefit`：userId/courseId/routes[{routeId,epochId}] → allowed/courseAllowed/matchedRouteId/matchedEpochId/sourceId。
- 先查课程有效 grant，再查 `route_entitlement` 有效来源 + `grant_route_member(source_id,epoch_id,course_id)`。
- `grant_route_member` 历史行不删除；来源状态由退款冻结/撤权控制。

学生接口：

- `GET /api/v1/routes/{routeId}/benefit-assignments?courseId=`。
- `GET /api/v1/benefit-assignments/{id}`。
- `POST /api/v1/benefit-assignments/{id}/attempts`。
- `GET /api/v1/benefit-assignments/{id}/progress|submissions`。
- 草稿/提交复用 `/api/v1/attempts/{id}/draft|submissions`；BENEFIT_CODE 进入代码任务，BENEFIT_CHOICE 按选择题判分。

### 3. 关键实现

1. 福利列表只返回该路线、该课程绑定且当前用户有该 epoch 资格的题；不把其他路线或未匹配 epoch 的题放进列表。
2. 福利详情隐藏标准答案/解析；提交成功后由 submission 详情返回解析或代码参考实现。
3. 历史 epoch 的老学员保留 grant；路线移除只关闭 epoch 投影，不删除 grant 或课程来源。
4. 新买家在移除后购买路线只获得当前成员（不含该课程）的 grant，因此旧题 403；路线重新加课形成新 epoch 后，新买家可访问绑定新 epoch 的新题。
5. 提交前重新调用学习验权，不依赖开始 attempt 时的旧结论；来源冻结后写请求直接拒绝，恢复后再提交成功。
6. 下架只改 assignment 状态：详情仍可读但 publicBody 为空、start attempt 409，旧 submission 仍可访问。
7. 教师下架/删除也重新检查当前课程与路线分配；调离后旧 token 无法继续操作。

### 6. 理解问题与精简回答

1. **为什么福利访问要查 grant_route_member，而不是只看当前路线成员？** 当前成员只说明“现在在路线里”，不说明购买时订单快照是否包含该课程；grant 是按购买/补发时 epoch 写入的历史资格。
2. **为什么老学员在课程被移出路线后还能访问？** 移除只关闭当前 epoch，不删除历史 grant；老学员的课程权益和旧 epoch 资格仍有效，历史题仍应可读。
3. **为什么新买家看不到旧题？** 新订单快照不包含已移除课程，学习不会给他写旧 epoch 的 grant；即使路线后来重新加课，也会形成新 epoch 和新题。
4. **为什么提交时还要再验权？** 开始 attempt 到提交之间可能发生退款冻结或来源撤销；写操作必须按最新状态校验，不能沿用开始时的旧授权。

### 6. 理解问题与精简回答

1. **为什么福利题复用正式作业工作台？** 选择题/代码 slot、草稿冲突、提交幂等和 AI 反馈逻辑相同；差异只在访问校验和数据源。复用避免两套编辑与判分逻辑漂移。
2. **为什么教师页要保留草稿的 routeIds？** 首次发布前服务端只把路线存在 draft_json，view.routes 为空；页面若不保留本地勾选，第二次保存会把路线当成被修改，发布也会失败。
3. **为什么路线福利页为空时不显示“未购买”以外的假题？** 服务端按课程权益和路线 epoch 资格过滤；前端只展示服务端允许的题，不能用静态列表绕过授权。
4. **下架后为什么仍能进详情？** 已提交的学生需要回看历史；新 attempt 被后端 409 拒绝，题面为空，避免继续作答。
