### 6. 理解问题与精简回答

1. **为什么规则首次发券后不能直接改？** 已发用户券保存的是规则版本快照；直接改会让旧券的解释和金额漂移。需要新增规则版本，旧券按原版本使用。
2. **为什么领取要同时锁活动、券项、规则和计数？** 活动状态、库存、个人限领和规则有效期必须来自同一时刻；只锁库存会把暂停活动或规则过期后的券继续发出去。
3. **为什么 `acquisition` 和库存都要唯一/条件更新？** `acquisition` 的请求键保证同一重试不重复发券；库存条件更新保证不同请求并发时不超发，两者解决不同维度。
4. **为什么用户券要保存有效期快照？** 规则以后可能新增版本；已领取的券必须固定自己的有效区间，释放或活动暂停不能改变原有效期。

- `POST /api/v1/trade/quotes` 支持 `couponSelection.mode=NONE/AUTO/MANUAL`。
- AUTO 由营销枚举 0～3 张券的全部合法组合与顺序；MANUAL 只枚举所选券的全部排列，全部必须有效且优惠大于 0，否则返回 `COUPON_COMBINATION_INVALID`。
- 报价响应增加 `couponPlan[]`，每张券含 `userCouponId/applyOrder/baseCent/discountCent/allocation[]`；路线报价的课程行剩余金额同步扣减券分摊。
- `GET /api/v1/trade/quotes/{id}` 在 CALCULATING 时轮询营销任务，READY 后原子回填金额、`resultHash` 和 `coupon_plan_json`。

### 3. 关键算法

1. **基数**：只使用已有课程抵扣后的当前 `remainingCent`；免费课、已抵扣课和余额为 0 的课程不进入覆盖范围。
2. **逐券顺序**：每张券重新计算覆盖课程余额 B，先判 B>0 且 B>=门槛；折扣券优惠为 `floor(B*(10000-payRateBps)/10000)` 再取上限；实际优惠 `min(期望优惠,B,全单剩余-100)`。
3. **分摊**：按覆盖课程当前余额的比例分摊，Base 用 `BigInteger` 精确乘除，尾差按余数降序、courseId 升序补齐；每张券分摊之和等于实际优惠。
4. **最优与并列**：总优惠降序、张数升序、有效期向量升序、实际使用券 ID 向量升序；手选保持所选券全量参与。
5. **同来源**：以 `sourceType + sourceGroupId` 判断；活动券同活动最多一张，为 S15 积分兑换项目保留不同来源类型。
6. **异步**：500ms 未完成返回 CALCULATING，任务落 `pricing_job`；交易轮询营销状态。租约 30 秒，恢复用条件 `claimLease` 抢占，`finish` 必须带原 lease token，旧 worker 不能覆盖新结果。

### 6. 理解问题与精简回答

1. **为什么优惠券要按“顺序”枚举而不是简单相加？** 后一张券的门槛基数是前一张券分摊后的余额；折扣券和满减券交换顺序会产生不同总优惠，必须枚举排列。
2. **为什么分摊用 BigInteger 和尾差规则？** 金额是整数分，比例分摊会出现除不尽；先精确算整数商，再按余数和 courseId 固定补齐，才能保证每张券分摊之和恰好等于优惠且结果可复现。
3. **为什么同活动限制放在搜索剪枝而不是最后过滤？** 同活动第二张券一旦参与，就会改变后续券的基数；最后过滤可能把唯一最优组合剪掉，必须在搜索时就禁止。
4. **为什么异步任务需要 lease token？** 计算超时后旧线程可能仍在跑；恢复者重新计算时，旧线程不能用自己的结果覆盖新结果。token 条件更新就是 fencing。

内部接口：

- `POST /int/v1/coupon-locks/prepare`：交易下单时调用；校验 quoteId 对应定价任务、pricingHash、券归属/状态/有效期，按券 ID 排序锁行并写锁券记录。
- `POST /int/v1/coupon-locks/use`：仅接受 PAID 且本订单 LOCKED，核销用户券。
- `POST /int/v1/coupon-locks/release`：仅接受本订单 LOCKED，释放回 AVAILABLE，不改有效期。
- `POST /int/v1/coupon-locks/recover`：宽限期后按交易订单状态补齐；PAID 核销，CLOSED 或订单不存在时释放。
- `POST /int/v1/orders/status-batch`：交易只读批量订单状态，供营销对账。

学生接口变化：

- `POST /api/v1/trade/quotes` 的 AUTO/MANUAL 结果成为下单券方案来源。
- `POST /api/v1/orders` 的 `selectedCouponIds` 必须与报价 `couponPlan` 精确一致；订单返回 `coupons[]`。
- 页面：`/checkout` 增加推荐最优/手选/不用券、逐券实际优惠和分摊；`/orders/:id` 增加优惠券明细。

### 3. 关键实现

1. 交易下单先重算当前商品/权益基础 hash，再与报价保存的 `pricingHash` 组合校验；券 ID 集合必须与报价计划完全一致，不能在请求里静默换券。
2. 订单写入 `order_coupon` 快照后调用营销 prepare；营销按券 ID 排序 `FOR UPDATE` 锁用户券行，条件更新 AVAILABLE→LOCKED，任何一张失败整事务回滚。
3. 券锁成功后订单才置 WAIT_PAY；交易事务若在锁券后失败，会立即补发 release，营销对账再兜底孤儿锁。
4. 支付回调在交易事务提交后调用 use；取消、到期和无效收款在关闭事务提交后调用 release。使用 afterCommit 避免“营销已核销但交易回滚”的跨服务半写。
5. use 不重新检查券有效期，只检查本订单 LOCKED，因此锁券后即使券过期，支付成功仍可核销；release 不修改 validUntil，释放后已过期券不能再报价/锁定。
6. 营销恢复任务只处理超过 120 秒的 LOCKED 记录，CLOSING/WAIT_PAY 不动；订单不存在视为建单回滚并释放。

### 6. 理解问题与精简回答

1. **为什么锁券要按券 ID 排序并一次全成或全失败？** 排序固定加锁顺序可降低死锁概率；全成或全失败保证订单不会出现“只锁了部分券”的不可解释状态。
2. **为什么锁券放在下单而不是支付？** 下单时学生已经确认方案，必须把券预留到支付截止，否则同一张券可能被另一个订单抢走；锁后过期仍可支付是 ORD-04C 的要求。
3. **为什么支付核销放在 afterCommit，并且还要对账？** 交易和营销是两个数据库，不能用本地事务同时提交；先提交支付事实再核销，失败时由营销按订单状态补核销，避免跨服务半写。
4. **为什么释放不能延长券的有效期？** 券的有效期是领取时固定的事实；取消只恢复可用状态，过期券释放后仍然是过期券，否则等于变相延长活动。
