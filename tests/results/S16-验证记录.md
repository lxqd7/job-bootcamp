### 7. 理解问题与精简回答

1. **为什么演示种子通过 API 而不是直接插 SQL？** 这样种子经过与真实用户相同的校验、事务、版本和权限路径，能发现“只有直插数据库才能成立”的假闭环；只有积分/债务等测试夹具直接改库，并明确标注用途。
2. **为什么安全矩阵要同时覆盖 401 和 403？** 401 表示未认证，403 表示已认证但角色/范围不足；两者混用会掩盖“普通学生被当成未登录”或“管理员权限被错误继承”的问题。
3. **为什么 DTO 敏感字段要递归扫描而不是只看类型定义？** 序列化框架、嵌套对象和旧字段容易让密码哈希、内部 token 或 AI prompt 从非预期层级泄漏；对真实响应做递归检查更接近攻击者视角。
4. **为什么需求族矩阵保留 NOT_RUN？** 真实支付/云媒体/模型账号没有凭据时不能伪造 PASS；NOT_RUN 明确区分“本地闭环已验证”和“真实外部联调未执行”。

## S16-b 故障停机、Outbox 重放与恢复（2026-11-24）

### 1. 范围

- 依次制造 Rabbit、营销、学习、worker、Redis 故障并恢复，检查事件不丢、不重复、状态可恢复。
- 补跑 S09-b 未知支付/退款撤权与 S14-b 撤回先到乱序场景。
- 故障注入为本机进程级：停 broker/服务/Redis，再启动同一 JAR；不是多实例网络分区或生产集群演练。

### 2. 故障场景与结果

`tests/acceptance/s16b-fault-recovery.mjs`：**13 项 PASS**。

1. **Rabbit 停机**：创建公开笔记并停 Rabbit，教师评优成功，互动 `outbox_event` 保持 NEW/重试状态，营销无流水；重启 Rabbit 后 outbox SENT，营销消费并只发一次 5 分。
2. **营销停机**：停 marketing 后教师评优，互动事件已发到 Rabbit 但无积分流水；营销重启后从队列消费，inbox PROCESSED 且只有一条 EXCELLENT 流水。
3. **学习停机**：创建订单后停 learning，MOCK 支付成功，订单 PAID 但 fulfillment 保持 PENDING；重启 learning 后 trade 发权事件被消费，订单 DONE，学生获得课程权益。
4. **worker 停机**：assignment 以 `AI_MOCK_DELAY_MS=20000` 启动，提交代码任务后停 assignment；等待租约过期，再以延迟 0、5 秒租约重启，worker 恢复任务并转为 GRADED。
5. **Redis 停机**：历史月份月榜在 Redis 可用时返回 77 分；停 Redis 后回退 MySQL 仍返回 77；重启 Redis 并重建缓存后仍一致。
6. **未知支付/退款撤权**：`s09b-refund-channel-api.sh` **98 项 PASS**，覆盖 UNKNOWN→查询→COMPLETED、撤权失败重试、券保持 USED、退款不重复。
7. **撤回/奖励乱序**：`s14b-reward-revocation-api.sh` **87 项 PASS**，撤回先到 pending、奖励后到同事务净 0。

### 3. 数据一致性检查

- Rabbit/营销恢复后同一笔记只有一条 EXCELLENT 流水和一条 inbox 记录。
- 学习恢复后订单 fulfillment DONE，学生 `/me/courses` 出现课程；未产生重复权益。
- worker 恢复后同一 submission 只完成一次，`ai_user_slot` 释放。
- Redis 故障期间月榜回退 MySQL，恢复重建后分数一致。
- S09-b/S14-b 检查未出现负余额、重复发分、重复退款或券重复核销。

### 5. 理解问题与精简回答

1. **为什么 Rabbit 停机后事件仍在 outbox？** 业务事务先提交事件行，relay 才投递；停机只让投递失败并退避重试，不会丢业务事实。
2. **为什么营销停机时事件可以先发到 Rabbit？** 营销队列是持久队列；互动 outbox 只负责把事件可靠送到 broker，营销恢复后按 inbox 幂等消费。
3. **为什么学习停机时订单不能直接标记 DONE？** 支付确认和发权是两个服务的事实；只有 learning 实际建立权益并回传后，fulfillment 才能完成，否则会出现“订单成功但没有课程”的假完成。
4. **为什么 worker 停机要等租约过期？** 租约防止旧 worker 与新 worker 同时完成同一任务；旧实例消失后，新实例必须等 lease 到期才能安全接管并写结果。

## S16-c 真实并发、100 候选性能、EXPLAIN 与契约（2026-11-24）

### 1. 范围与修复

- 真实 MySQL、本地单实例执行：100 个相同积分事件、100 个兑换请求抢 10 库存、同一代码 attempt 100 次提交、100 张券 AUTO 最优组合。
- 检查课程/订单/月榜/笔记/问答/兑换列表 EXPLAIN、JSON 响应 envelope/错误码/报价字段、全量 `mvn verify` 与前端构建。
- 发现并修复：100 个相同积分事件并发插入 `inbox_event` 唯一索引时触发 MySQL 死锁，部分请求 500 且延迟约 30 秒。修复为同一 JVM 内按 `consumer+eventId` 串行执行，并对数据库死锁做 5 次短退避重试；事件仍是事务性 inbox 幂等。

### 6. 理解问题与精简回答

1. **为什么 100 个相同积分事件会死锁？** 所有请求同时尝试插入同一个 `(consumer,event_id)` 唯一索引，InnoDB 在等待/回滚竞争时可能选择死锁牺牲者；唯一键保证最终只有一条，但应用必须把死锁当作可重试冲突，而不是 500。
2. **为什么同 JVM 按 eventId 串行化不等于放弃数据库幂等？** 它只是减少单实例内无谓的唯一键竞争；跨实例仍靠 `inbox_event` 唯一键和事务，数据库仍是最终权威。
3. **为什么 100 候选 p95 高还可以接受？** 这是本机冷/热 JVM 和异步轮询的观测值，不是生产 SLA；方案没有为了速度跳过全部组合或返回非最优券，性能优化不能牺牲最优优惠。
4. **为什么 EXPLAIN 要看列表查询而不是只测接口延迟？** 接口延迟会被缓存、JVM 热度和数据量掩盖；EXPLAIN 能直接看到索引是否命中，先排除全表扫描等结构性风险。
