## S13-a 问答、匿名投影与内容治理（2026-11-23）

### 1. 需求与实现范围

- 需求：SOC-01、SOC-02、AUTH-02/03。
- 新增 interaction 服务（18086、bc_interaction）：问题、回答、评论、管理员隐藏与匿名追溯。
- 学生有课程权益可提问/回答/评论；教师只答负责课程并显示 TEACHER 身份；管理员不默认通过学生接口读问答。
- 匿名问题投影为“匿名学员”、authorId 为空，owner 通过 mine 管理。
- 问题删除/隐藏后整线程不可公开访问；回答/评论逻辑删除；子内容保留在库中。
- 管理员隐藏必须 reason 并审计；匿名称号追溯使用 anonymous:trace 独立权限和审计。
- 笔记/采集、点赞、问答页面和教师工作区属 S13-b/c。

### 2. 数据与接口

V1 表：

- `question(course_id,lesson_id?,author_id,title,body,anonymous,state,last_answer_id?,revision,created_at,updated_at)`。
- `answer(question_id,author_id,author_role,body,state,like_count,revision,...)`。
- `comment(answer_id,author_id,body,state,like_count,revision,...)`。
- `moderation_action(target_type,target_id,admin_id,action,reason,created_at)`。

接口：

- `GET/POST /api/v1/courses/{id}/questions`
- `GET/PATCH/DELETE /api/v1/questions/{id}`
- `GET/POST /api/v1/questions/{id}/answers`
- `GET/POST /api/v1/answers/{id}/comments`
- `PATCH/DELETE /api/v1/answers/{id}`、`/comments/{id}`
- `POST /api/v1/admin/content/{type}/{id}/hide`
- `GET /api/v1/admin/questions/{id}/author?reason=`

### 3. 关键实现

1. 读取分别调用 learning `access:check`（学生）和 course `teachers:scope`（教师）；管理员直接访问学生问答 403。
2. 匿名问题对 owner 和其他学生都返回 authorId=null、authorDisplay=“匿名学员”；owner 的 mine=true 供前端显示管理入口，无法从 DTO 反查作者。
3. 教师回答 author_role=TEACHER，视图同时返回角色和昵称；学生回答为 STUDENT。昵称通过 user profiles:batch 获取，失败时降级为“学员 #id”。
4. 问题编辑/回答/评论均使用 revision 乐观锁；非 owner 编辑 403，旧 revision 409。
5. 问题 DELETED/HIDDEN 后，问题详情、回答列表、评论列表都返回 404；回答/评论行仍在库中，满足审计和保留策略。
6. 回答/评论逻辑删除后从公开列表移除；被删除回答的评论接口 404。
7. 管理员 hide 必须 reason（空/超长 400），写 moderation_action；匿名追溯必须 reason，返回真实作者并写 TRACE_AUTHOR 审计；教师无该权限。
8. 无 AI 自动回复、采纳、悬赏或人工批改入口。

### 6. 理解问题与精简回答

1. **匿名问题为什么对 owner 也不返回 authorId？** owner 需要的是管理能力，不是身份字段；用 `mine` 表达归属即可，避免任何客户端从 DTO 反查匿名作者。
2. **问题删除后为什么不物理删回答/评论？** 审计、举报核查和管理员追溯需要保留原始内容；公开访问通过父线程状态和查询过滤阻断。
3. **管理员隐藏和匿名追溯为什么要分开接口？** 隐藏是内容治理，追溯是身份审计；两者权限码不同，追溯必须填写原因并留下审计记录。
4. **为什么教师回答要存 author_role？** 角色是回答发布时的业务事实，不能靠事后查询用户当前角色推断；教师调岗后历史回答仍应显示教师身份。

## S13-b 笔记、采集与退款后管理例外（2026-11-23）

### 1. 需求与实现范围

- 需求：SOC-03、SOC-04、SOC-04A、AUTH-02/03。
- 原创笔记公开/私密；公开只面向有课程权益学生和负责课程教师。
- 采集副本每人每原文唯一，保存作者快照，强制私人，原文更新/删除不覆盖副本。
- 本人退款后仍可在“我的笔记”读取、编辑、删除自己的原创和采集副本；不能新增/采集或访问他人社区内容。
- 笔记逻辑删除、管理员隐藏和审计；课程/小节删除后的展示与 S13-c 页面未做。

### 2. 数据与接口

- `note(owner_id,course_id,lesson_id?,position_ms?,type,source_note_id?,source_author_snapshot?,body,visibility,state,content_revision,excellent)`，U(owner,source_note)。
- `note_version(note_id,content_revision,body,visibility,created_at)`。
- API：`GET/POST /courses/{id}/notes`、`GET /me/notes?type=`、`GET/PATCH/DELETE /notes/{id}`、`POST /notes/{id}/collect`。

### 3. 关键实现

1. 公开列表只查 VISIBLE + COURSE_PUBLIC + ORIGINAL；教师按负责课程过滤，私有/采集副本不会进入列表。
2. 采集在同一事务检查原文公开可见、不能采自己、课程权益，写 sourceNoteId、正文副本和作者昵称/角色快照；并发重复由唯一键与 DuplicateKey 返回同一副本。
3. 采集副本 `visibility=PRIVATE` 由服务和数据库 CHECK 双重保证；PATCH 改公开返回 400。
4. 原文编辑/删除不影响副本正文和快照；副本编辑也不回写原文。
5. `/me/notes` 与本人 GET/PATCH/DELETE 不做课程权益检查，退款后仍可管理；新增/采集/他人公开读取仍要求当前权益。
6. 逻辑删除 state=DELETED，公开列表排除，owner 列表保留 state；管理员隐藏 state=HIDDEN，公开读取 404，owner 仍可见，写 moderation_action。
7. note_version 在创建/每次内容更新时插入，保留内容历史。

### 6. 理解问题与精简回答

1. **为什么采集副本必须私人？** 采集是个人学习副本，不是原作者公开内容的再发布；允许公开会把别人的笔记变成新的传播源，也会绕过原作者对公开范围的控制。
2. **为什么原文更新不覆盖副本？** 副本是采集时的快照，保留作者和内容；自动跟随原文会让用户以为自己保存的内容被悄悄替换。
3. **为什么退款后本人还能管理笔记？** 笔记是个人内容，不是课程视频或他人社区内容；SOC-04A 明确保留本人管理，但收回新增/采集和公共访问权。
4. **为什么采集用唯一键而不是先查后插？** 并发双击或多设备同时采集时，先查后插会生成两个副本；数据库唯一键保证每人每原文只有一份，重复请求返回同副本。

## S13-c 点赞、问答/笔记页面与教师工作区（2026-11-23）

### 1. 需求与实现范围

- 需求：SOC-01、SOC-02、SOC-03、SOC-04、SOC-04A、SOC-05、PTS-03。
- 点赞只作用于回答/评论，每人每条最多一个有效记录；可取消、不能自赞；无权访问或隐藏/删除的目标不能点赞；点赞不产生积分。
- 学生端：课程问答（提问、回答、评论、点赞）、课程公开笔记、笔记详情、我的笔记。
- 教师端：负责课程答疑（教师回答并显示身份）、负责课程公开笔记只读工作区。
- 管理员内容列表/治理页面仍不在本小任务范围内。

### 2. 数据与接口

- `like_record(user_id,target_type,target_id,active,created_at,updated_at)`，主键 `U(user_id,target_type,target_id)`，普通索引 `(target_type,target_id,active)`，CHECK 限定 ANSWER/COMMENT。
- API：`PUT /api/v1/likes/{type}/{id}`、`DELETE /api/v1/likes/{type}/{id}`；回答/评论读取增加 `likeCount`、`liked`。
- 学生页面路由：`/courses/:id/questions`、`/courses/:id/notes`、`/notes/:id`、`/me/notes`；教师页面：`/teacher/questions`、`/teacher/notes`。

### 3. 关键实现

1. 点赞先对目标回答/评论行 `SELECT ... FOR UPDATE`，同一目标的并发点赞/取消在数据库行锁上串行，避免计数丢失或重复 +1。
2. 锁定目标后复核父问题/父回答可见、课程权益（学生）或教师负责范围（教师），再查询当前用户的 `like_record FOR UPDATE`。记录不存在则插入 active=TRUE；存在但已取消则复用同一行更新 active，而不是删除重建。
3. `like_record` 是联合主键，没有 MyBatis-Plus 的 `@TableId`，首次实现调用 `updateById` 时运行期报 `Invalid bound statement`；改为显式 `UPDATE ... WHERE user_id AND target_type AND target_id`，验收中实际触发并修复。
4. 取消点赞把 active 置 FALSE；重复取消不再减计数，返回当前计数，保证幂等；计数器下限为 0。
5. 自赞在服务端按目标作者判断并返回 400；隐藏回答、删除评论在锁定目标时即 404，不产生新点赞。
6. 点赞仅更新互动库记录和计数，不写积分、不写 outbox、不发通知。
7. 学生问答/笔记页直接调用 interaction API；教师页复用同一套线程/公开笔记接口，服务端按当前负责课程过滤，前端只负责展示教师徽标与只读状态。

### 6. 理解问题与精简回答

1. **为什么点赞计数不直接 `UPDATE ... SET like_count=like_count+1`？** 先锁目标行再基于读取值更新，能把“记录 active 状态”和“计数”放在同一事务里判断；单纯 +1 无法区分重复请求，也无法保证与记录状态一致。
2. **为什么取消点赞不删除记录？** 删除后无法区分“从未点赞”和“取消过”，并发下还可能出现删除/插入竞争；保留行并把 active 置 FALSE，主键天然保证一人一条，重复取消也幂等。
3. **为什么点赞也要校验课程权益？** 点赞是社区互动入口，若能绕过权益直接按 ID 点赞，会泄漏内容存在性并允许无权益用户参与；服务端必须在写操作上验权，不能只靠页面隐藏按钮。
4. **为什么教师公开笔记页不提供采集？** 采集是学生个人学习行为，教师工作区定位是只读了解负责课程内容；给出采集入口会模糊教师与学生权限边界，也与需求中“教师只查看公开笔记”不一致。
