# S09 退款与资金对账验证记录

本文件按阶段合并记录 S09 的验收证据；S09-b/S09-c 完成后继续追加。

## S09-a 退款意向、固定清单与来源冻结（2026-11-22）

### 1. 需求与实现范围

- 需求：REF-01、REF-02、REF-02A、REF-04、REF-05（S09-a 只做受理和资格预检，不发起渠道退款）。
- 学习侧受理 `refund_intent`，分配申请序列，保存购买时固定小节清单、完成快照和 `acceptedAt`，冻结本订单来源。
- 交易侧自动检查：已支付事实、snapshotHash、7×24 小时窗口、进度≤20%、抵扣依赖。
- 待付依赖订单没有渠道单时自动关闭并释放预留；渠道结果未知保持 PENDING；已支付依赖返回 `REFUND_DEPENDENCY`。
- 渠道退款状态机、真实退款、撤权/恢复、抵扣边释放、退款页面属 S09-b/c。

### 2. 数据与接口

新增：

- learning `V5__refund_intent.sql`：
  - `refund_intent(id, request_id, order_id, user_id, accepted_at, user_sequence, paid_at, snapshot_hash, product_type, completed_count, total_count, source_id, source_version, state, reason, active_order_id)`；
  - `refund_intent_lesson` 保存申请时固定的 `course_id/lesson_id/completed/completion_sequence`；
  - `active_order_id` 唯一约束保证同一订单最多一个 ACCEPTED/PROCESSING 申请。
- 学习 API：
  - `POST /api/v1/orders/{id}/refund-applications`，返回 202、requestId、acceptedAt、sequence、state、完成数/总数；
  - `GET /api/v1/refund-applications/{requestId}`，仅本人可见。
- 交易内部接口：
  - `GET /int/v1/orders/{id}/refund-basis?userId=`：返回 paidAt、snapshotHash、paidCent、逐课程固定 lessonIds；
  - `POST /int/v1/refunds/qualify`：返回 QUALIFIED/REJECTED/PENDING、reason、amountCent。
- 网关新增 learning-refund 路由，先于 trade 的 `/orders/**` 匹配。
- 支付事件中路线成员的 `lessonIds` 和 `refundLessonIds` 补齐为本次新购付费课的小节，免费/已抵扣课不计入退款基准。

### 3. 关键实现

1. **学习本地线性化**：退款申请先取交易 basis，再在 learning 的 `user_guard` 行锁内重新检查活动申请、冻结来源、插入 `refund_intent` 和固定小节行，最后提交。申请序列与进度完成共用同一个用户锁，谁先提交谁决定完成数是否计入。
2. **固定清单**：清单来自订单创建时的 `order_lesson`，不是当前课程目录；删除小节、课程改版、重新购买都不会改变本申请的分子/分母。
3. **冻结**：`entitlement_source` 从 ACTIVE→FROZEN 并递增 `lifecycle_version`。访问、播放授权、我的课程/路线、购买来源选择都只认 ACTIVE，所以冻结来源立即失效；同一用户的其他 ACTIVE 来源保留。
4. **资格预检**：交易检查订单 PAID、支付事实、snapshotHash、`acceptedAt < paidAt + 7×24h`、`completedCount × 5 ≤ totalCount`，并查询 `deduction_link`。
5. **依赖协调**：来源被路线订单用作抵扣时，若依赖单 WAIT_PAY 且没有活动渠道单，交易关闭依赖订单并释放预留/抵扣边；依赖单已 PAID 或 `deduction_link` 已 COMMITTED 则拒绝退款；渠道结果未知保持 PENDING，不提前释放。
6. **失败恢复**：资格拒绝时学习在 `user_guard` 内把来源恢复 ACTIVE、递增生命周期版本，并把 intent 置 REJECTED、清空 active_order_id。重复申请同一订单返回原 requestId，不重复冻结。

- 重复申请同一订单返回同一 requestId，`refund_intent` 只有 1 条，不重复冻结。
- 冻结来源后，新播放授权返回 403；申请查询返回 PROCESSING。

### 6. 理解问题与精简回答

1. **为什么退款受理放在学习服务，而不是交易先受理？** 退款资格要用完成小节数和用户锁下的完成顺序；学习本地事务是唯一能同时分配 sequence、保存完成快照、冻结来源并阻止后续授权的线性化点。
2. **为什么退款清单不能用当前课程目录？** 课程可能增删小节，当前分母会漂移；REF-02 要求购买时固定清单，即使小节后来删除，仍按原分母和已有完成状态计算。
3. **为什么冻结来源后其他来源仍然可用？** 退款只针对本订单授予的来源；同一课程可能还有免费、其他订单或路线来源，访问检查任一条 ACTIVE 即可，不能误伤其他合法权益。
4. **为什么待付依赖要自动关闭，已支付依赖要拒绝？** 未支付的抵扣预留不能无限占用退款窗口，可以安全关闭；已支付或已提交的抵扣是真实权益关联，只能先退依赖路线，再退来源，否则会破坏已购权益。
## S09-b 退款状态机、渠道查询与撤权恢复（2026-11-22）

### 1. 需求与实现范围

- 需求：REF-03、REF-04、REF-05、REF-06。
- 用户退款进入渠道状态机：`FREEZE_CONFIRMED → CHANNEL_PENDING / CHANNEL_UNKNOWN → REVOKE_PENDING → COMPLETED`；
  明确未退款关闭走 `CLOSE_RESTORE → CLOSED`；暂时失败保留 `CHANNEL_PENDING` 重试。
- 渠道结果未知时先查询，不重复提交退款；成功后再撤权，撤权失败保留 `REVOKE_PENDING` 继续恢复，不二次退款。
- 已用优惠券不退还、不恢复；退款金额只取订单实付。

### 2. 数据与接口

新增/调整：

- trade `V8__refund_state_machine.sql`：扩展 `refund` 状态；增加 `user_id`、`trade_state_version`、`source_version`；`intent_id` 唯一；用户退款按 kind/state/updated_at 扫描。
- learning 内部：`POST /int/v1/sources/revoke`、`POST /int/v1/sources/restore`，携带 refundId/intentId/orderId/userId/expectedSourceVersion；来源状态按 `lifecycle_version` fencing。
- trade 内部：`POST /int/v1/refunds/start`；公开管理端 `POST /api/v1/admin/refunds/{id}/reconcile`；开发场景 `POST /api/v1/dev/refunds/{orderId}/scenario`（仅 MOCK + ADMIN，默认关闭）。
- 支付渠道边界增加 `queryRefund`；MOCK 可切换 `UNKNOWN/COMPLETED/CLOSED/FAILED`。

### 3. 关键实现

1. `UserRefundService.start` 按 intentId 幂等创建退款单；第一次渠道请求只使用一个 `refundNo`，状态持久化到 `refund` 后执行。
2. `CHANNEL_UNKNOWN` 状态只调用 `queryRefund`：已成功则转撤权，明确关闭则恢复来源，仍未知保持；不会再次调用 `refund`。
3. `CHANNEL_PENDING`（临时失败）重试时复用同一 `refundNo`；成功后进入 `REVOKE_PENDING`。
4. 渠道成功后调用学习撤权：来源 `FROZEN → REVOKED`，递增生命周期版本，退款 intent 置 COMPLETED；撤权失败只保留 `REVOKE_PENDING`。
5. 渠道明确关闭调用学习恢复：来源 `FROZEN → ACTIVE`，退款 intent 置 CLOSED；不修改券状态。
6. 退款成功不操作营销券：`user_coupon` 和 `coupon_lock` 保持 USED；订单实付金额进入退款单。

### 4. 已执行验证

`tests/acceptance/s09b-refund-channel-api.sh`：**98 项 PASS**（Rabbit + `PAYMENT_MOCK_SCENARIO_ENABLED=true`）。

- 默认渠道成功：refund COMPLETED、来源 REVOKED、intent COMPLETED、订单实付 990；重复 reconcile 保持 COMPLETED。
- UNKNOWN：refund CHANNEL_UNKNOWN、来源 FROZEN、intent PROCESSING；把 MOCK 改为 COMPLETED 后 reconcile 先查询再撤权，最终 COMPLETED/REVOKED。
- 明确关闭：refund CLOSED、来源恢复 ACTIVE、intent CLOSED。
- 临时失败：refund CHANNEL_PENDING；改成功并 reconcile 后完成，且复用原 refundNo。
- 模拟撤权失败：refund 保持 REVOKE_PENDING（不再次发起渠道退款）；恢复来源可撤后 reconcile 变 COMPLETED，原渠道退款号不变。
- 带券订单退款成功：券仍为 USED、锁记录仍为 USED。
- `s09a-refund-intent-api.sh` 101 项 PASS（改用 UNKNOWN 保持 frozen，避免 S09-b 成功退款影响 S09-a 断言）；S06-a 回归 PASS；后端 36 个测试通过。

### 6. 理解问题与精简回答

1. **为什么 UNKNOWN 只能查询不能重试退款？** 渠道可能已经受理，只是响应丢了；重复提交可能造成两笔退款。先按 `refundNo` 查询，拿到明确成功或关闭事实再推进。
2. **为什么渠道成功和撤权要分成两个状态？** 渠道退款成功不可逆；撤权是学习库的独立事务，可能暂时失败。保留 `REVOKE_PENDING` 可以只重试撤权，绝不再次调用退款。
3. **为什么渠道明确关闭要恢复来源？** 关闭表示没有退款发生，订单权益应当恢复；恢复只针对 FROZEN，已 REVOKED 的来源不能被旧恢复命令复活。
4. **为什么退款不退券？** 券在支付成功时已经整张核销，退款只退实付金额；退回券会让用户通过退款重新获得已消费优惠。
