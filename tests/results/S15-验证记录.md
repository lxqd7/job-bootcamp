## S15-a 兑换项目管理与配置版本（2026-11-24）

### 1. 需求与实现范围

- 需求：PTS-07、PTS-07A。
- 管理员配置兑换券规则、积分价格、总库存、每人累计限兑、开放窗口和上下架状态。
- 新建项目默认下架；修改价格/库存/限兑/规则/时间必须带 revision，过期 revision 返回 409。
- 库存不能低于已兑换数量；结束时间已过不能上架。
- 项目切换券规则或调价只影响后续兑换，已兑换券仍引用原规则版本。
- 下架/重新上架不清空已兑换数量，也不重置用户累计限兑。
- S15-b 的实际扣分/授券/并发兑换与 S15-c 学生兑换页未在本小任务实现。

### 2. 数据与接口

- marketing V9 `exchange_project(id,name,rule_id,points_price,stock_total,stock_used,per_user_limit,state,open_at,close_at,revision,created_at,updated_at)`。
- 约束：`points_price>0`、`stock_total>=stock_used>=0`、`per_user_limit>0`、`open_at<close_at`；索引 `(state,open_at,close_at)`、`rule_id`。
- 管理 API：`GET/POST /api/v1/admin/exchange-projects`、`GET/PATCH /{id}`、`POST /{id}/online|offline`。
- 管理页面：`/admin/exchange-projects`，使用现有券规则列表选择规则。

### 3. 关键实现

1. 创建项目时校验名称、券规则存在、积分价、库存、每人限兑和开放窗口；初始状态 OFFLINE、revision 0、stockUsed 0。
2. PATCH 锁项目行并校验 revision，库存下限为当前 stockUsed；规则可切换，已发出的 user_coupon 仍引用旧 ruleId。
3. 上下架使用 revision 条件；重复上架幂等；结束时间不晚于当前时间时拒绝上架。
4. 上下架只改 state，不触碰 stock_used 和 `acquisition_counter`，为 S15-b 的累计限兑保留事实。
5. 管理列表支持 ONLINE/OFFLINE 筛选，返回规则键/版本、积分价、库存使用量、限兑和 revision。
6. 网关只暴露 `/api/v1/admin/exchange-projects` 给已认证请求，服务端再校验 ADMIN 角色；学生/教师/匿名均拒绝。

### 6. 理解问题与精简回答

1. **为什么兑换项目要引用券规则版本，而不是复制优惠字段？** 券规则已经不可变版本化，兑换只决定“发哪张券”；引用 ruleId 能保证已兑券的优惠内容和有效期不随后续配置变化。
2. **为什么上下架不重置限额和库存？** 下架只是停止新兑换，已兑换事实仍然存在；重新上架应继续累计原先的个人限兑和库存消耗，否则用户可通过下架/上架绕过限制。
3. **为什么库存不能低于已兑换数？** stockUsed 是已发券的事实，库存若低于事实会让“已兑换数/总库存”出现负数空间，也会破坏后续扣减和前端展示。库存只能收缩到事实下限。
4. **为什么配置修改必须带 revision？** 管理员可能在两个页面同时调价或改库存。revision 让并发修改显式冲突，避免后保存的旧页面静默覆盖新价格或库存。

## S15-b 原子兑换、库存并发与来源隔离（2026-11-24）

### 1. 需求与实现范围

- 需求：PTS-07、PTS-07A、ORD-03I、ORD-04A、ORD-04G。
- 学生兑换时同一本地事务完成：扣可用积分、库存 +1、每人累计兑换 +1、发券、acquisition 和 exchange_record。
- 项目行锁串行同一项目的库存/限兑判断；账户行锁串行扣分；同 requestKey 幂等重放，跨项目复用 key 冲突。
- 兑换券来源为 EXCHANGE，记录项目 ID；活动券来源为 ACTIVITY，两者计数与来源隔离。
- 兑换只扣可用余额，不增加/扣减月榜，`EXCHANGE` 流水 rankDelta=0。
- 失败（库存/限兑/余额/版本/窗口）整体回滚，不留下扣分或库存变化。

### 2. 数据与接口

- marketing V10 `exchange_record(id,user_id,project_id,project_revision,request_key,points_spent,user_coupon_id,ledger_id,balance_after,created_at)`；`U(user_id,request_key)`、`U(user_coupon_id)`。
- API：`POST /api/v1/exchange-projects/{id}/exchanges`，header `Idempotency-Key`，body `expectedRevision`。
- 积分流水 `EXCHANGE` 业务键为 `userId:requestKey`，记录 `-points`、`balanceDelta=-points`、`debtDelta=0`、`rankDelta=0`。
- acquisition/acquisition_counter 使用 `source_type=EXCHANGE`、`source_item_id=projectId`；券 `source_type=EXCHANGE`、`source_group_id=projectId`。

### 3. 关键实现

1. 事务锁顺序固定为 exchange_project → coupon_rule → points_account → acquisition_counter，和活动领券/积分更新路径保持清晰边界。
2. 项目行锁内复核 expectedRevision、ONLINE、开放窗口和库存；规则行锁内计算固定/天数有效期，首次发券标记 `issued`。
3. `spendForExchange` 在账户锁内检查可用余额，写 EXCHANGE 流水并更新余额；不触碰月榜。
4. 计数用 `acquisition_counter` 的 `(user,EXCHANGE,projectId)` 行，项目上下架和规则切换不会重置。
5. 发券、acquisition、exchange_record 与扣分/库存/计数同事务；任一校验失败或唯一键冲突整体回滚。
6. requestKey 为空生成 UUID；同一用户同一 key 重放返回原 exchange/coupon/balanceAfter；跨项目复用 key 返回 409，避免把别的项目结果误认为本次结果。
7. 并发同 key 由 exchange_record 唯一键兜底；并发不同 key 由项目行锁串行，只有成功请求产生一次积分流水和库存/计数变化。

### 6. 理解问题与精简回答

1. **为什么扣分和发券必须同一个本地事务？** 两者都在营销库，若先扣分再发券失败，用户会白扣积分；同一事务可以在库存耗尽、限兑、券插入或记录唯一键失败时把余额和计数一起回滚。
2. **为什么项目行锁放在账户锁前？** 所有同项目兑换都先经过项目行，库存/限兑/窗口在同一锁下判断；固定锁顺序能避免不同请求以相反顺序拿锁导致死锁。
3. **为什么同 requestKey 跨项目要拒绝？** 幂等键代表“同一个兑换请求”。若允许跨项目复用，客户端重试时可能把另一个项目的结果当成当前项目的成功结果，余额和券都对不上。
4. **为什么兑换流水 rankDelta 必须为 0？** 积分兑换是消费，不是当月获得；月榜统计所得分，兑换只减少可用余额。写 0 才能让月榜和余额分开。
