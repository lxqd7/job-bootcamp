# 交易、权益与退款设计

日期：2026-11-17。实施契约；关联CRS、BUY、ORD、REF、BEN。数据名见数据字典，接口见接口契约。本文件定义交易算法与状态边界，不表示代码已实现。

## 1. 金额与发布校验

所有金额为整数分，后端long＋乘法BigInteger中间值；不使用double。单课付费price>=990，免费price=0；路线至少含两门课程、至少一门付费，0<routePrice<付费单课价总和。每门付费课套餐分摊>=100分；管理员发布、改价、换成员均校验。已发布路线受单课改价影响时，课程改价与关联路线价格版本在课程库同事务校验；不合法则拒绝该次变更并列出需调整的路线，不改历史快照。

分摊函数 allocate(T,weights)：q_i=floor(T*w_i/sum(w))，余数r_i=(T*w_i)%sum(w)；剩余分依r降序、courseId数值升序各加1。权重只含正金额课程，空集合且T>0报错。按单课价把路线价格分摊一次；已有课程抵扣分摊价值，免费课0，未拥有课剩余为待购买金额。全部已有则不创建付费单，不授路线资格。

用户已拥有A/B/C中A，单价100/200/300元、路线480元：分摊80/160/240，抵扣80，应付400。不按A历史实付计算。并列尾差：3课各990分、路线1000分→334/333/333（courseId升序）。当仅一门未拥有，其分摊至少100分，因此不存在抵扣后0～99分订单。券计算和分摊由营销文档定义；最终满足商品金额=课程抵扣+券优惠+实付。

下单保存商品版本、分类祖先ID集合、分摊、抵扣来源、券顺序、实际用额、每课程最终金额及退款清单，不随课程调价、分类变化重算。

内容版本：ONLINE课程/路线的编辑在校验成功后同事务生效并发布新版本，页面明确“保存并生效”；DRAFT/OFFLINE只保存工作数据，publish才产生对外版本。已有学员读取最近发布目录，下架只停止新销售。影响售价、目录、分类或路线成员的变更同步更新相关商品快照；旧订单仍用原快照。多资源更新按ID升序加锁。

## 2. 权益账本与来源选择

source类型FREE/COURSE_ORDER/ROUTE_ORDER；来源状态ACTIVE/FROZEN/REVOKED。grant绑定用户、课程及来源；访问查询至少一条ACTIVE来源，路线福利另查route_entitlement。仅在目标课程的course_grant中筛选ACTIVE来源，按grantedAt升序、同时间按grantId数值升序选择最早获得的课程权益，返回sourceId及sourceGrantId。不能用路线来源acquiredAt代替该课程grantedAt：1日买路线、5日才新增C，而3日已单买C，应优先3日的单课来源。同一来源可支持多条抵扣，不因预留换选较新来源。

路线购买仅给本次未拥有付费课程建立grant；已抵扣课沿用原来源。免费课独立FREE来源，路线退款不撤销。后续新增付费课属于该路线来源，后续新增免费课独立FREE；同一来源/课程唯一，幂等。已有其他来源的新增课仍可保留该路线自身授予来源；这是后续加课授予，不重算原订单抵扣或退款基准。

免费领取以课程库受理事务为准：校验当时免费、保存claimId/user/course/version/acceptedAt及Outbox，再由学习幂等建立FREE来源。免费转付费不取消改价前已受理的领取；新请求按新价格判断。内部短期凭据过期只重新签发同一claim，不重做已受理资格。接口返回PROCESSING或FULFILLED，领取状态可按claimId查询，不能因服务延迟丢掉免费资格。

已拥有ACTIVE单课权益不重复卖课，返回ALREADY_OWNED；同课正在退款且无其他ACTIVE来源，返回REFUND_IN_PROGRESS，处理完再重购，历史完成保留。

grantedAt记录取得该课程权益的生效时刻：免费领取用acceptedAt，订单快照成员与付款时仍有效的窗口新增成员用paidAt，付款后新增成员用joinedAt。异步授予和重放不会将任务处理时间写成grantedAt。

若剩余待购买付费金额为0，按BUY-04走顺序学习，无付费单或新路线资格。若仍有尚未领取的免费成员，显示逐门免费领取入口，不为它们收费。

## 3. 下单与并发

交易库user_trade_guard(userId)行锁串行化同一用户的创建/付款处理/退款关联修改。学习库user_guard串行化来源状态、购买预留、进度首次完成和退款申请受理；不在持有数据库锁时远程调用。

创建流程：
1. POST quotes取得可信课程snapshot及学习权益，计算Quote；返回quoteId/hash、明细，报价有效5分钟，不占券和权益。
2. POST orders校验幂等键，先创建CREATING、expiresAt=创建时间+30分钟。只接受quoteId、quoteHash、selectedCouponIds；商品信息从本人报价读取，拒绝客户端金额字段。
3. 学习preparePurchase在user_guard内重新选最早来源并建立purchase_hold（订单、course、source），同时返回权益版本。为待购课程建立pending_course锁（userId/courseId唯一）；同用户已有重叠待付订单返回ORDER_CONFLICT及已有订单ID，避免双单按“未拥有”同时卖同课。
4. 对比商品/权益/价格/券结果与用户确认hash，变动则终止创建、补偿并返回QUOTE_CHANGED。不得静默更换券或来源；quote只是预览，步骤3后新变化以服务端准备结果为准。
5. 营销按订单all-or-none锁券并校验当前有效；交易保存完整快照后进入WAIT_PAY。失败进入CREATE_FAILED，重试清理已准备步骤；不可部分锁券后允许支付。
6. 付款请求仅WAIT_PAY可创建渠道单；CREATING不可支付。支付通知确认后source holds转COMMITTED关联，清pending_course；新grant本地来源由学习幂等创建。支付成功订单状态与发权状态分开。

来源预留与退款：preparePurchase只接受ACTIVE且没有进行中refund_intent的来源（已结束申请不阻止新操作）。退款受理会阻止新预留；已有待付订单不能无限占住退款期限：先记录申请时点，再协调取消这些订单并核对渠道。若其在该依赖订单的有效付款/取消边界前已支付，即使晚于来源退款申请，也构成真实关联：来源退款以REFUND_DEPENDENCY拒绝并恢复来源，依赖单再完成发权；已准备的有效购买不能被新退款意图无声取消。若确认未付则释放预留继续原申请。未知付款保留申请处理中，不能把网络延迟变成申请超期。取消后有效收款的识别仍按渠道实际付款时间，不能因本地取消日志覆盖事实。

抵扣关系仅从新购买订单指向早已有效的来源订单；交易在user_trade_guard分配payment_sequence，按来源订单payment_sequence小于依赖订单payment_sequence校验，因此不形成环。退款成功前不释放COMMITTED边；免费来源无来源订单退款边，但保存来源审计。

## 4. 支付与关闭

状态：
- order：CREATING→WAIT_PAY→PAID；WAIT_PAY→CLOSING→CLOSED；CREATING→CREATE_FAILED。关闭后发现有效早付可进入RECONCILING。只有收款和相关来源/券均可证明一致才转PAID；出现渠道相互矛盾的证据则暂停自动资金/权益修复并人工对账，不能自动更改其他已支付订单。
- payment：INIT/PENDING/UNKNOWN/SUCCEEDED/CLOSED；原始收款流水不可删除。
- fulfillment：PENDING/RUNNING/DONE/ATTENTION，与PAID独立。

有效付款区间[createdAt,expiresAt)，取消时还需paidAt<cancelRequestedAt。恰好截止/取消时刻认定不满足“之前”，核实收款后原路退，不发权益。仅接受渠道验签且商户/币种CNY/金额/orderId一致的结果。paidAt必须为可信渠道时间；时间精度不足以判定边界则UNKNOWN，查渠道明细或运维证据，不凭回调到达时间猜。

取消/到期请求持久化关闭意图，查询并关闭渠道单；确认未收款且不可继续付款才释放券和预留。渠道未知时每30秒查询，5分钟后降为每5分钟，30分钟标需关注，继续查询。不能到达本地TTL就自动释放。用户可看处理状态，管理员只能查询、重试、录入可审计渠道证据，不能凭空标付款或篡改金额。

晚付/重复真实收款：每个channelTransactionId唯一记账；有效主收款最多一笔。超期限或额外收款不发第二份权益，创建SYSTEM_RETURN退款（无学习进度/七天限制），金额为实际额外收款。已用券不恢复；未形成有效购买的系统退回在确认收款处置及关闭后释放锁券，券原有效期不延长。验签失败返回渠道失败，不执行状态变化。

mock提供独立后台测试控制：付款成功、延迟通知、UNKNOWN、关闭成功/失败、重复收款、退款结果未知；仅dev/test、ADMIN、审计。学生只能正常发起模拟付款，不能指定付款时间或模拟结果。

一个渠道支付单对应不可变payment_request，payment只记录查询确认的真实收款流水（同请求可有多笔异常收款）。每笔payment至多一个SYSTEM_RETURN，以system_return_payment_id唯一；用户退款成功后再次请求不得超过原实收累计可退额。回调与查询共用同一处理器，确认receiptId之前先验签，不保存可供未验签报文抢占的去重键。

## 5. 路线版本与历史资格

课程库每次成员变化写不可变route_version及route_member_epoch：加入生成epochId、joinedAt，移除写removedAt；再次加入用新epoch。商品快照保存version/epochId。课程/路线逻辑删除保留版本，不物理清除交易引用。

paidAt为渠道事实。授课集合=订单快照课程 ∪ 支付时仍有效的支付窗口新增epoch课程。支付后新增epoch也授予，已移除的下单快照课程不撤权。支付时历史集合按成员区间[joinedAt,removedAt)查询。课程内部同刻变更按revision有序，但不能用revision推断外部付款先后；付款时间精度与成员变更重叠且会影响集合时进入RECONCILING，以渠道证据核实，不用当前集合或任意顺序替代。付费用户持有未来资格后，支付之后短暂加入再移除的课也要发放，不能仅扫描当前成员。

学习grant_route_member保存sourceId/epochId/courseId/qualifiedAt（用户由source反查）；消费新增事件根据来源paidAt与epoch区间判断。延迟支付通知后的恢复按paidAt重放历史epoch，发放和会员状态在学习本地事务检查；FROZEN来源记录待发放但不开放，REVOKED不再开通；不能旧支付消息把撤销来源复活。

福利题首次发布绑定courseId与一组routeId/epochId，发布后课程与路线绑定不可直接替换，需新建题；正文修改仍发布新版本，历史绑定不变。旧题历史访问按原绑定校验，避免教师改路线无声撤权。课程移除前发布的题，拥有该epoch资格的老学员保留访问；移除后的新购者不获得旧epoch资格。新题发布只能绑定当前有效epoch。重新加入时新epoch福利题供持有该新epoch资格者；旧题仍按旧epoch。教师必须同时有当前课程和对应路线分配，题内容/学生记录只读权限分别检查。

grant_route_member覆盖合法取得路线资格的全部成员（含抵扣课和免费课），不只覆盖新发grant。冻结期间的新增epoch也记待授予事实；恢复时补发，撤销时不开放，不丢弃冻结期间事件。

## 6. 申请时退款资格与冻结

退款申请入口由学习服务受理，再交交易处理，避免“先在交易计时、后查学习进度”的竞态。UI点击时间和网关到达时间不作为业务申请成功时间；接口202返回acceptedAt及sequence才表示已受理。这是服务端提交事务的线性化点，必须在页面/接口说明。

学习本地user_guard事务：
1. 校验本人订单的已支付投影已就绪；未就绪返回ORDER_SYNCING，可重试，不能伪报已受理。
2. 锁用户行，分配nextSequence，数据库时间acceptedAt；保存refund_intent及订单snapshotHash。统计固定lessonId清单中completionSequence<=申请sequence的完成事实（历史完成也计入）。
3. 保存分子/分母、acceptedAt、paidAt、来源状态；设置退款意图屏障并FROZEN该来源，阻止新购买预留及学习新授权；outbox通知交易。用户其他ACTIVE来源仍可使用。
4. 进度首次完成使用同一user_guard分配sequence；先提交完成就计入退款，后提交则不计。无需跨机器时钟比较，学习消息延迟不影响本地完成事实。
5. 交易核验同一snapshotHash、acceptedAt < paidAt+7天，完成数*5<=总数，真实支付及关联条件；不合格发送恢复命令并给出具体原因；不是让管理员审批。

分母必须>0，付费商品创建订单时强制快照含至少一节视频（路线对本次新购付费课分别检查）。坏数据导致0分母不自动认定0%，报DATA_INTEGRITY并恢复未退款来源，进入排障；正常发布与下单双校验防止此情况。

退款状态：VALIDATING→FREEZE_CONFIRMED→CHANNEL_PENDING/CHANNEL_UNKNOWN→REVOKE_PENDING→COMPLETED；不合格REJECT_RESTORE→REJECTED；明确未退且关闭CLOSE_RESTORE→CLOSED。资格通过后保持原acceptedAt不重算；自动恢复、重试不丢资格。渠道请求唯一refundNo；超时先query，未退且可继续时复用同一refundNo提交，不另造编号。

退款成功：先落渠道事实；持续撤销source及路线资格，再解除本订单对其他来源的COMMITTED关联，最后COMPLETED。渠道成功而撤权失败不得再次退款。FROZEN期间新视频授权拒绝，已签发媒体短期令牌风险见媒体文档。正常积分、完成与作答记录不删除；福利/作答历史当前仍验权，个人笔记例外。

交易退款终态写入同事务产生trade.refund-state-changed.v1。学习消费后将对应refund_intent同步到COMPLETED/REJECTED/CLOSED，释放活动申请唯一约束；终态消息延迟时先保持申请处理中，不提前解除未完成流程。相同intent重复受理返回原requestId，不新冻结一次。

学习收到paid投影后即使grant未全部建立，也先保存退款意图。后续activate读取refund_intent：处理中创建FROZEN来源，已退款维持REVOKED；不能以“来源不存在”为由重新ACTIVE。

## 7. 跨服务恢复与验证

每步按orderId/refundId＋commandType唯一，协调步骤保存step/status/attempt/nextRetryAt/errorCode；远程调用事务外；每次恢复先查询已完成事实。学习服务独占source.lifecycleVersion：状态变化本地递增。FREEZE/REVOKE/RESTORE携带expectedSourceVersion，比较成功后返回新sourceVersion；相同commandId返回原结果，不拿交易aggregateVersion覆盖学习版本。旧ACTIVATE不能覆盖FROZEN/REVOKED。仅在退款资格被明确拒绝、或渠道已确认未退款且退款流程关闭时接受RESTORE。

必须测试：报价后改价/权益变化；同用户重叠订单；抵扣prepare与退款并发；两条路线依赖同来源；支付乱序、晚到/晚付、取消同刻；发权中断；新增/移除/重新加入的epoch重放；已退款后支付事件重投；退款申请与50%阈值进度并发；退款跨7天处理仍按acceptedAt；撤权失败恢复无二次退款。具体样例见任务书S06～S09。
